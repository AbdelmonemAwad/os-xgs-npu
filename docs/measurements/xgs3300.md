# XGS 3300 - what has been measured on it

Numbers taken on one appliance, with how each was taken and what it does not mean. They are here
rather than in [octeon-tx-reference.md](../families/octeon-tx-reference.md) because a measurement
belongs to a **board**, not to a family: a second XGS 3300 with a different kernel or a different
cable would produce different figures, and the reference page should carry conclusions rather than
readings.

**Nothing here is a projection.** Every line was read off this machine.

## The machine

| | |
|---|---|
| appliance | Sophos XGS 3300, assembly `AMDA0202-0004`, platform `xgs1us` |
| host | AMD Ryzen Embedded V1780B |
| coprocessor | Cavium OCTEON TX CN8365, PCI `177d:a300` at `pci0:1:0:0` |
| operating system | OPNsense 26.7 / `FreeBSD 15.1-RELEASE-p1 stable/26.7-n283674-12334a596709 SMP` until 2026-10-03; OPNsense 26.7.5 / `FreeBSD 15.1-RELEASE-p3 stable/26.7-n283949-083dc7025377 SMP` since (the update is [below](#a-kernel-update-must-not-cost-the-front-ports); the previous kernel stays on the disk as `kernel.old` with a module of its own) |
| driver | `octep`, built on the appliance against that kernel's own headers |
| front ports | 12, all presented as `oxp0`..`oxp11` |

## Round trip and loss

**Method.** `ping -f` from the appliance to the router on the other end of a copper panel port's
cable, 30,000 full-size frames, interface counters read either side.

```
elapsed 6 s
in   30022 pkts   1512 bytes/pkt    5003 pps    60 Mbit/s
out  30003 pkts   1513 bytes/pkt    5000 pps    60 Mbit/s
0.0% packet loss
round-trip  min 0.091   avg 0.193   max 0.508 ms
```

**What it is.** A latency figure and a loss figure. Nothing dropped in 30,000 full-size frames.

**What it is not.** A throughput figure. `ping -f` sends the next probe when the last reply arrives,
so it is bound by the round trip: 5,000 packets a second against a 0.193 ms round trip is the same
number written twice.

## The transmit ceiling

**Method.** A UDP sender that never waits (`blast.c`, below), aimed at **a panel port with no cable
in it** so the frames cross the whole host-to-coprocessor path and die at a dark switch port without
touching anything anyone else is using. Five seconds, 1472-byte payloads. The coprocessor's own
named counters were read either side of the run over the `rpc` facility.

```
offered and accepted by the driver     2,628,609     525,722 pps
FPCNTR_RX_KN                          +2,627,710     the coprocessor took them
FPCNTR_FROM_KN_TO_WIRE                +2,628,609     and chose the wire for every one
FPCNTR_TX_DROP_QUEUE_FULL             +2,210,885     84% refused at its egress queue
to the wire                              416,825      83,365 pps = 1,023 Mbit/s
```

**The account closes.** 1,023 Mbit/s is line rate for a gigabit port at 1534 bytes a slot with the
preamble and the interframe gap, so everything the driver posted either left at line rate or was
dropped by the coprocessor's egress queue - which is the correct thing for it to do.

**So the number that matters is what the driver accepts:**

| | packets a second | |
|---|---|---|
| the driver accepts | **525,722** | measured |
| a 1G port needs | 81,486 | **6.5x headroom** |
| a 10G port needs | 814,863 | **65% of line rate** |

For the eight copper panel ports and the two 1G cages this driver is nowhere near the bottleneck.
Only the two 10G SFP+ cages are capped.

**Read that table one port at a time.** It says what the driver accepts for a single interface, and
that is what it was measured as. The appliance's total is a different number and a smaller one - see
"the aggregate ceiling" below, which was measured afterwards and is one gigabit for all twelve ports
together.

## Removing a redundant write

**Method.** The same generator and the same dark port, before and after the change in #173, which
stopped the transmit path zeroing the frame it was about to copy over.

| payload | before | after | |
|---|---|---|---|
| 1472 bytes | 525,722 pps | **535,142 pps** | +1.8% |
| 64 bytes | 595,558 pps | **607,232 pps** | +2.0% |

**What it tells us beyond the gain.** 525,722 packets a second is 1.9 microseconds each, and a
redundant 1,514-byte write is not what that is made of. The next suspect is the one MMIO write per
packet - the input doorbell.

## What load on one front port costs the other eleven

**Method.** `tools/octep-fairness.sh`. The generator is paced now - `blast` takes a packets-per-second
argument and sends in bursts of about a millisecond - so the load is a known rate rather than
whatever one core can manage. Each step offers six seconds of traffic at one rate on a **dark** front
port while an ordinary `ping` runs underneath it on the port that carries the appliance's **WAN**,
and the coprocessor's own named counters are read either side of every step.

```
with no load at all: 0.0% loss, 0.177 ms average, 0.209 ms worst

target_pps  offered_pps  wire_Mbit   wan_loss  wan_avg wan_worst  drop_queue_full
      5000         5000         61      4.2%    0.168    0.228                 0
     10000        10000        123      0.0%    0.169    0.203                 0
     25000        25000        307      8.3%    0.170    0.207                 0
     50000        50000        614     29.2%    0.173    0.225                 0
    100000       100000       1227     31.2%    0.173    0.250           100,229
    200000       200000       2454     33.3%    0.171    0.187           696,534
    400000       400000       4909     72.9%    0.183    0.228         1,904,034
   unpaced       535176       6568     60.4%    0.173    0.193         2,711,514

with no load again:  0.0% loss, 0.178 ms average, 0.225 ms worst
```

**What it says.** The twelve interfaces are not independent. A flood aimed at one of them costs the
others their packets, and it starts long before anything is reported as dropped: at 50,000 packets a
second the WAN loses **29%** of its echoes while `FPCNTR_TX_DROP_QUEUE_FULL` has not moved at all.
Below 10,000 packets a second the loss is indistinguishable from this appliance's ordinary
background, which is why the soak script defaults to that rate.

**And the latency never moves.** 0.17 ms average at every rate, 0.25 ms at worst, the same as idle.
A frame for another port is sent at once or thrown away; it is never delayed. Whatever is full is not
a queue deep enough to wait in.

## Where those packets are lost, counter by counter

**Method.** 200 echo requests at 50 a second, under three conditions, with five instruments read
either side: the interface's own transmit count, the coprocessor's `FPCNTR_RX_WIRE` and
`FPCNTR_FROM_WIRE_TO_KN_FORCED`, the driver's `dp.rx_done`, and the host's ICMP input histogram.

| | requests posted | coprocessor took from the wire | forwarded to the host | driver delivered | echo replies at the stack | loss |
|---|---|---|---|---|---|---|
| no load | 202 | 210 | 210 | 218 | 200 | 0.0% |
| 50,000 pps elsewhere | 202 | 161 | 161 | 153 | 126 | 37.0% |
| unpaced elsewhere | 200 | 72 | 72 | 72 | 55 | 72.5% |

Four things follow, and they narrow the fault to one place:

- **The host posts every request** in all three runs. Nothing is refused on this side, and
  `net.inet.ip.intr_queue_drops` stayed at zero throughout.
- **The coprocessor forwards everything it receives.** `RX_WIRE` and `FROM_WIRE_TO_KN_FORCED` are
  equal in every run, so no LIF gate and no TCAM entry is dropping anything.
- **But it receives less and less from the wire as the load rises** - 210, then 161, then 72. The
  replies are not coming back, because the requests are not getting out.
- **A second, much smaller loss is inside the host**: 161 forwarded against 153 delivered.

So the frames die after this host counted them as sent and before the gateway ever saw them, on a
path every front port shares.

**The suspect, found by reading the transmit path afterwards rather than by guessing:** every
interface copies its frame into **one** buffer - `sc->dp_txbuf`, a single page - posts an
instruction carrying that buffer's physical address, rings the doorbell and releases the mutex. The
coprocessor reads the memory itself, afterwards, on its own schedule. The next frame overwrites the
previous one. At 1.9 microseconds a packet an echo request posted by one port is overwritten by
another port's traffic before it is read, and what goes out in its place carries the other port's
tag. That would produce exactly this: posted, counted, never seen, and no counter anywhere
reporting a drop. **It was built, and the next section is the same sweep again.**

## The same sweep, with a buffer per instruction slot

**Method.** Identical to the sweep above - same script, same rates, same appliance, same kernel -
with one change in the driver: `sc->dp_txbuf`, one page shared by every interface, became
`sc->dp_txbufs`, 256 buffers at the ring's own stride, and a frame is copied into the buffer
belonging to the slot its instruction will occupy. Nothing else was touched. The appliance was
rebooted because the datapath attaches once per coprocessor boot, and it came back with twelve
interfaces, the WAN lease and the default route, unattended.

```
with no load at all: 0.0% loss, 0.178 ms average, 0.229 ms worst

target_pps  offered_pps  wire_Mbit   wan_loss  wan_avg wan_worst  drop_queue_full
      5000         5000         61      0.0%    0.169    0.210                 0
     10000        10000        123      0.0%    0.172    0.245                 0
     25000        25000        307      0.0%    0.170    0.219                 0
     50000        50000        614      0.0%    0.174    0.385                 0
    100000       100000       1227      0.0%    0.181    0.240           100,274
    200000       200000       2454      0.0%    0.175    0.255           698,090
    400000       400000       4909      0.0%    0.173    0.200         1,890,791
   unpaced       528885       6490      0.0%    0.173    0.203         2,660,027

with no load again:  0.0% loss, 0.180 ms average, 0.224 ms worst
```

| offered on one port | WAN loss before | WAN loss after |
|---|---|---|
| 5,000 pps | 4.2% | **0.0%** |
| 25,000 pps | 8.3% | **0.0%** |
| 50,000 pps | 29.2% | **0.0%** |
| 400,000 pps | 72.9% | **0.0%** |
| unpaced, about 530,000 pps | 60.4% | **0.0%** |

**Zero at every rate, including 6.5 Gbit/s offered at one port while another carries the
appliance's internet.** The twelve interfaces are independent now, and they were not before.

**A second counter agrees without being asked.** `FPCNTR_TX_WIRE_ERR` used to move whenever
anything was loaded - 25 to 76 of them in a fifty-second window at a mere 10,000 packets a second.
On the fixed driver it does not move at all, through 16 million frames in a thirty-second window at
full rate. Frames that had been overwritten mid-flight were reaching the MAC malformed, and the far
side was counting them; now there are none to count.

**What this says about the earlier numbers.** The egress ceiling is unchanged - `drop_queue_full`
tracks the old run step for step - so the one-gigabit aggregate below stands exactly as measured.
What changed is that reaching it no longer costs the other eleven ports their traffic.

## The aggregate ceiling is one gigabit, not twelve

**Method.** Two dark front ports loaded at the same time, six seconds each, and the arithmetic of
`FPCNTR_FROM_KN_TO_WIRE` minus `FPCNTR_TX_DROP_QUEUE_FULL` - what the fast path chose to send, less
what it threw away for want of room. The soak was running concurrently at 10,000 packets a second on
a third dark port, which is included in these figures.

| offered | chosen for the wire | refused, queue full | reached the wire | |
|---|---|---|---|---|
| one port at 50,000 pps | 329,588 | **0** | 329,588 | 54,931 pps |
| two ports at 50,000 pps | 664,182 | 159,759 | 504,423 | **84,070 pps = 1,023 Mbit/s** |
| two ports at 200,000 pps | 2,462,180 | 1,960,315 | 501,865 | **83,644 pps = 1,019 Mbit/s** |

One port at 614 Mbit/s passes untouched. Two ports at 614 Mbit/s each do not: a quarter of the
frames are refused, and what gets through is **1,023 Mbit/s** - the same figure the single-port
ceiling run produced, and the same figure again when the offered load is quadrupled. One gigabit is
not a per-port limit on this appliance. It is the whole datapath.

**It is a bit rate, not a packet rate**, which is worth proving because the two look identical from
one frame size:

| payload | ports | reached the wire | |
|---|---|---|---|
| 1472 bytes | two at 200,000 pps | 82,582 pps | 1,013 Mbit/s |
| 64 bytes | two at 200,000 pps | 405,964 pps | 422 Mbit/s, nothing refused |
| 64 bytes | one, unpaced | 591,380 pps | 615 Mbit/s |
| 64 bytes | two, unpaced | **1,053,385 pps** | **1,096 Mbit/s** |

**A million small frames a second go through the stage that caps full-size frames at 84,000.** In
bytes the two agree: 129 MB/s and 137 MB/s. So the shared stage drains about a gigabit of frame
bytes a second whatever the frames are.

**What it is not.** It is not a limit of this driver: the coprocessor accepted 6.5 Gbit/s over PCIe
in the same runs - `FPCNTR_RX_KN` counted every frame - and put a gigabit of it on the wire. It is
not a measurement of twelve ports doing useful work either; every frame here died at a dark port,
and a cabled port has a link partner and flow control that a dark one does not.

**And it is not the switch uplink.** That was the first suspect and it is now ruled out by reading
the switch itself. `xgs-mdio -a 0 2 <port>.0` on the coprocessor returns each port's status
register, and the uplink is the one that differs:

| switch port | status | link | speed field |
|---|---|---|---|
| 0, the uplink to the coprocessor | `0x0f4d` | up | **3** |
| two cabled copper ports | `0x0e0f` | up | 2, which is 1000 Mbit/s |
| the dark copper ports | `0x000f` | down | - |
| the two 1G cages | `0x0249` | down | 2 |

The only difference between the uplink and a gigabit port is one bit: speed 3 rather than 2, which
on this family means **above 1000 Mbit/s**. The uplink also carries a different connection mode -
13 against 15 - which is what a 10G mode looks like beside a 1000BASE-X one.

**So the gigabit is inside the coprocessor's fast path**, not on the wire between it and the switch.
The remaining candidate is a shaper: `FPCNTR_TX_DROP_SHAPER_INV` exists, and the `rpc` enumeration
has `QOS_SET_SHAPER_RATE` at 23 and `QOS_GET_SHAPER_RATE` at 24. Neither request structure is in the
module's DWARF, so reading the rate back is the next piece of archaeology rather than the next
command.

## Two counters that were wrong, and how the measuring found them

**Received bytes were doubled.** The first run charged an interface **3,026 bytes for every
1,514-byte frame**. `ether_input_internal()` adds the received byte count itself unless the driver
claims `IFCAP_HWSTATS`, which this one does not, so counting it in the driver as well doubled it.
The packet count was right, because that file increments no `IPACKETS`. Fixed in #171; afterwards
the two directions agree at 1512 and 1513 bytes a packet, which is what a ping flood should show.

**`Opkts` is offered load, not what left the port.** In the ceiling run it read **6,432 Mbit/s out
of a gigabit port**: the 84% the coprocessor dropped, counted as sent. The driver cannot see those
drops per packet - they belong to the far side and only `rpc` reads them - so read `Opkts` as
offered load and `FPCNTR_TX_DROP_QUEUE_FULL` as the truth about what the wire took.

## The receive path, and why every number above is a transmit number

Everything on this page until now was measured by **sending**. A generator on a dark front port,
thousands of packets a second, hours of soak, and the loss figures that came out of it are real. Not
one of those measurements could ever have filled a **receive** ring, and a defect had been sitting in
that half of the datapath the whole time.

What it looked like: the appliance held its lease, routed, resolved, and answered the first hop in
0.6 ms. `traceroute` ran clean to six hops. And a `fetch` of a 16.7 MB file returned **0 bytes in
25 s**, every time, while three consecutive `opnsense-update` runs installed nothing at all.

Four measurements say where it is not:

| | |
|---|---|
| the line | 16.7 MB to a PC on the same ONT at 4,354 kB/s |
| the host stack and `igb0` | 64 MB in **737 ms**, 90,933 kB/s, with no `octep` in the path |
| the coprocessor's own ledger | six counters moved during a failing download and **balanced exactly**: `RX_WIRE +180`, `TX_KN +180`, `FROM_WIRE_TO_KN_FORCED +180`, and **no drop counter moved** |
| the front port | `Ierrs 0  Idrop 0  Oerrs 0` |

So the wire was fine, the host was fine, and the coprocessor believed it had delivered everything.

### The two numbers that had never been put side by side

The far side's count of what it handed over, against the host's count of what it took:

```
FPCNTR_TX_KN              +19      handed to the host
driver dp.rx_done          +0      taken by the host
all oxp interfaces Ipkts   +0
```

`dp.state` then showed real WAN frames sitting in host memory, addressed to the WAN port's own MAC,
with `OUT_CONTROL` reading **idle** - the block had written them and finished. `R_OUT_CNTS` low half
read **1,532**: packets the host had never acknowledged. And all eight MSI-X vectors were frozen,
their sum exactly equal to `dp.intr_taken`, so not one interrupt had fired since the stall began.

One `dp.service=1` by hand delivered **1,550 frames in a single call**. With a service loop running,
the first hop answered **8/8 at 0.0% loss**, and the interrupts resumed on their own.

### The mechanism

`octep_dp_intr` took **one pass** at the ring. A pass reads `R_OUT_CNTS`, takes at most `RSIZE`
packets, and acknowledges those. The block raises its interrupt when the count **crosses** the
interrupt level - not while it sits above it. So a burst bigger than one pass leaves the count above
the level with nothing left to re-cross it, and the ring is dead.

And `octep_dp_service()` had exactly two callers: that handler, and a sysctl written by hand. There
was no periodic receive path, so a lost edge was not a hiccup - it was permanent, until a reboot.

That is the whole symptom set. A ping never fills a ring, so a ping always worked. A download fills
one immediately, so a download never worked - and from that moment reception was dead for
**everything**, which is why the ping that had just succeeded started failing too.

### After the fix

The handler now drains until the ring reads empty, bounded at `OCTEP_DP_OQ_DRAIN_ROUNDS`, and a
callout services every armed ring twenty times a second whatever the interrupts are doing.
(Every servicer drains now and the bound is in packets; and that callout, whose service was one
pass, turned out to be a way of leaving a ring with packets in it: [a visit is not a pass](../findings/a-visit-is-not-a-pass.md).)

The same fetch, on the same appliance, over the same front port:

```
16,697,068 bytes in 29 s, fetch reporting 1,049 kB/s
```

and the instruments for that one download:

| | | |
|---|---|---|
| `dp.intr_drained` | **1,824** | handler entries that needed a second pass |
| `dp.rxwd_runs` | **11** | interrupts genuinely lost, and caught by the timer instead |
| `R_OUT_CNTS` low half | **0** | the ring fully drained |

`rxwd_runs` is the number worth keeping an eye on. Eleven lost edges in one 16 MB download is not a
rounding error, and before there was a timer under them, eleven was ten more than it took.

**And `rxwd_runs` was read too strongly too.** Eleven is how many times the timer found packets in
a ring, and that is all it is. It finds some in a ring whose handler is on its way; and for as long
as its own service was one pass it was itself what left a ring with packets in it, to be found on
its next tick. No lost interrupt has been shown on this block. The number to keep an eye on is
`dp.rxwd_stalls`: [a visit is not a pass](../findings/a-visit-is-not-a-pass.md).

**And `intr_drained` was read too strongly when it was first published here.** This page said every one
of those 1,824 second passes was a stall under the old code. It was not: a second pass that finds three
more frames is an ordinary second pass, and a stall needs the count left above the interrupt level
*after* a pass. What the counter measures is how often one handler entry needed more than one pass,
which under load is most of them. The evidence for the stall is the measurement above - `TX_KN +19`
against `dp.rx_done +0`, 1,532 unacknowledged, eight vectors frozen - and the figure itself was also
inflated by a second defect, fixed separately: a pass used to report the register's reading rather than
what it had taken, so a round that delivered nothing still counted. (It counts the passes beyond the
first of any servicer's hold of a ring now, not only the handler's.)

Then the thing the stall had been blocking for three attempts: `pkg fetch -u` took the cache from 40
packages to **336 in 52 seconds**, having previously stalled at 41 over several minutes each time, and
`pkg upgrade` installed all 84 - `OPNsense 26.7` to **26.7.5** - with the datapath carrying it and all
twelve front ports still up afterwards. That download alone needed **59,675** second passes.

And with the appliance warm, three 16.7 MB fetches back to back:

```
run 1: 16,697,068 bytes in 7 s = 2,038 kB/s
run 2: 16,697,068 bytes in 3 s = 4,076 kB/s
run 3: 16,697,068 bytes in 3 s = 4,076 kB/s
```

**4,076 kB/s is the best of the three, against the 4,354 kB/s the same file reaches on a PC on the
same ONT.** That is 94% of it: the gap narrowed, it did not close. And the runs do not agree closely
enough to place it even that precisely - the first of the three was 2,038 kB/s, 47% of the PC figure,
and the fetch above them 1,049 kB/s, so one file spread 3,027 kB/s across four readings, eleven times
the 278 kB/s between the best run and the PC.

**The seconds printed beside those rates are not the rates' own timebase.** 16,697,068 bytes at
4,076 kB/s is 4.00 s and at 2,038 kB/s is 8.00 s - both exact, with kB read as 1,024 bytes - against
the 3 s and 7 s printed beside them, and the fetch above them reads 29 s where its rate implies
15.5 s. So the rates are averages over the transfer and the seconds are something coarser. No
transcript was kept to settle which, so read the rates and treat the seconds as indicative.

**What these runs establish** is that a download now completes, repeatedly, at the same order as the
line - #197 is gone. What they do not establish is a throughput figure for the datapath: 4,076 kB/s
is 33 Mbit/s on a gigabit front port, so what bounds these runs is the ONT and the far server. Nor a
clean receive path - the driver was still returning sixteen credits per packet where the block debits
about one, and a twenty-download loop still stalled on the tenth until #205 held the credit to the
grant.

## A kernel update must not cost the front ports

This is the circle, and it closed on this appliance on `2026-10-01`:

```
new kernel -> the module's stamp no longer matches -> bring-up refuses it -> no front ports
-> no WAN -> nothing can fetch the kernel sources that would rebuild the module
```

The refusal itself is right. A FreeBSD module declares its kernel dependency as a range, so within
`15.x` the loader accepts a module built against a different `15.x` kernel rather than refusing it,
and any structure that moved is then read at the wrong offset inside the kernel of a machine
carrying traffic. There is no loud failure to wait for. So the module is stamped with the kernel it
was built against, and a mismatch is refused.

**And the refusal costs more than the link.** OPNsense configures its interfaces from the devices
that exist at that point in the boot, and the assignments whose devices are absent are dropped out
of `/conf/config.xml` outright. One boot with the module refused removed `wan`, `opt1`, `opt2` and
`opt3` from the configuration here - the WAN's own DHCP assignment with them - and getting the module
right afterwards did not put them back. They were restored from `/conf/backup/`, which is the only
reason this is a paragraph and not a reinstall.

### The window

Between a kernel being installed and the host rebooting onto it, everything needed is present at the
same time:

| | |
|---|---|
| the old kernel is still running | so the module is loaded and the WAN is alive |
| the new kernel is already on disk | where `strings -a /boot/kernel/kernel` finds the source commit it was built from |

That is the only moment a kernel change can be followed, and `install/kernel-follow.sh` is that moment
made automatic. **Where to call it from took two attempts, and the first would never have run.**

### The hook level, which was checked rather than assumed

`rc.syshook.d/update` looks like the obvious home: the directory exists and OPNsense ships a script in
it. **Nothing on this appliance passes `update` to `rc.syshook`.** The callers pass `facility`, `stop`,
`start`, `monitor`, `upgrade`, `import`, `early` and `carp`. A hook placed at that level is read by
nobody - which is the most expensive kind of wrong, because it looks like a guarantee and it is a file.

`upgrade` is called, from `scripts/firmware/upgrade.sh`, and reading that script settles where in the
sequence it sits:

```
opnsense-update -u                 the packages
rc.syshook upgrade                 <-- the hook
opnsense-update -K -c ; -K         the pending kernel is applied to /boot HERE
reboot
```

So **the new kernel is not in `/boot` when the hook runs.** It is a set waiting in
`/var/cache/opnsense-update/.sets.pending/` with a marker beside it, and once it is applied the reboot
follows with no hook in between. Reading `/boot/kernel/kernel` is therefore too late at the one place
anything calls us.

So the follower looks in both places, staged first:

| | |
|---|---|
| a staged set, `kernel-<release>-<arch>.txz` | `tar -xOf <set> boot/kernel/kernel \| strings` reads its version without unpacking it; the pipe closes at the first match |
| `/boot/kernel/kernel` | the kernel the next boot will use, for when `-K` has already run |

### And a cron entry, which needs nobody's cooperation

Five minutes, from `src/etc/cron.d/octep`. When the stamp already matches - almost always - it is two
file reads and an exit. It is there because a hook depends on somebody calling it and this does not,
and because the `update` level proved that assumption worth paying for once. That FreeBSD's cron reads
`/usr/local/etc/cron.d` on this appliance was also tested rather than assumed: a probe entry written at
19:06:30 fired at 19:08:00.

Then one reboot brings the kernel and the module up together and nothing is done by hand.

Run by hand it is a no-op whenever the stamp already matches, and `DRY=1` says what it would do:

```
sh install/kernel-follow.sh
DRY=1 sh install/kernel-follow.sh
```

### It fails towards the ports, not away from them

- the build happens before anything is replaced, and a build that fails leaves the installed module
  and its stamp exactly where they were
- the hook exits 0 on every path, because an update that stops half way is worse than a module that
  needs rebuilding by hand; what a failure costs is a loud warning in the log
- `contrib/octep/build.sh` takes `KVER` so the stamp records the kernel being built **for** rather
  than the one running, which is the whole point before a reboot

### And following forwards must not mean falling off backwards

The new module is stamped for the kernel on disk, which is not the kernel running while it is built.
If the host boots the old kernel again - a rollback, a boot menu choice, an update that did not take
- that stamp is wrong in the other direction and the ports would be refused for the opposite reason
to the one they were being saved from.

So the module being replaced is kept beside it as `octep.ko.prev` with its own stamp, and the
bring-up script loads that one when its stamp is an exact match for the running kernel. This is not
`FORCE`: nothing is loaded on a guess, and a module that matches neither kernel is still refused.

### Tested

Proving the refusal branch used to mean unloading the driver, which on this appliance takes the
twelve interfaces, the WAN lease and the default route with it and needs a host reboot to undo. Two
small changes make it reachable instead: `bringup.sh` takes `CHECK=1`, which stops after the module
decision and says which one it would load, and the loader commands are variables so a test can
report the module absent without it being absent.

All seven on the appliance, with the datapath carrying traffic throughout:

| | |
|---|---|
| stamp already matches | no-op |
| `DRY=1` on a mismatch | reports, changes nothing |
| mismatch, for real | the previous module kept with its stamp, the installed one stamped for the kernel on disk - and the loaded driver was never touched, WAN at 0.0% loss during |
| `octep.ko` wrong, `octep.ko.prev` an exact match | `CHECK=1: would load /boot/modules/octep.ko.prev`, exit 0 |
| neither stamp matches | refused, exit 1 |
| a staged kernel set present | version read out of the `.txz`, reported as `read from: staged, waiting to be applied`, and the decision correct with both a matching and a stale stamp |
| cron reads `/usr/local/etc/cron.d` | a probe entry fired on the next minute boundary |

**And that row said `rebuilt` more strongly than the run could show.** Nothing in the follower as it
was merged could tell a rebuild from a reinstall. It built in `/root/npu/octep-sdp`, a tree assembled
by hand that persisted between builds, and the `make clean` meant to empty it was given no `SYSDIR`:
with no `/usr/src/sys` to fall back on, `bsd.sysdir.mk` stops with `Unable to locate the kernel
source tree`, and that error went to `/dev/null`. `kmod.mk` never re-points an existing `machine`,
`x86` or `i386` link, and the generated `bus_if.h`, `device_if.h` and `pci_if.h` are remade only when
their `.m` file is newer. So once the objects were newer than anything make could see, make would
compile nothing and the module already in place would be installed and stamped for the new kernel -
the silent wrong-offset load the stamp exists to prevent - and the only checks were that `make`
exited 0 and that an `octep.ko` was there. #205 found exactly that on the appliance, by review: a
module stamped `p3` whose `machine` link pointed into the `p1` tree.

**And the one case the follower exists for was not among the seven.** `fetch-sources.sh` printed its
`SYSDIR=` line at column zero only on the path where the tree was already there; where it had just
fetched one it printed it inside an indented hint, and the follower read it with an anchored `sed`.
So a run whose sources had to be fetched could only end in `could not get kernel sources`, and the
seven runs above all had the tree present already. The next day, on the one kernel it had to fetch
for, it fetched 341 MB, verified the tree, reported that it could not get the sources and left the
module unbuilt. Both ends were fixed in #205.

## Stopping the receive path before an interface is freed

Found by review rather than by a crash, which is the only reason it is written down calmly.

A servicer reads `dif->ifp`, stores it in each mbuf's `rcvif`, and hands the chain to `if_input()`.
Detaching an interface calls `ether_ifdetach()` and then `if_free()` on that same ifnet. Nothing
connected the two, so a detach could free an ifnet while a servicer still held mbufs pointing at it -
inside the kernel of a machine carrying traffic.

Two things made it reachable. `octep_dp_stop()` detached the interfaces **before** releasing the
interrupt handlers and the watchdog, so both servicers were live for the whole of the detach. And
`if_input()` was called **after** the ring's busy flag was released - deliberately, so the ring was
free while the stack worked - which meant the busy flag could not be used to tell whether a servicer
was still holding an ifnet.

Every path that reached it is deliberate: `dp.stop`, `dp.if_del`, a device detach, `kldunload octep`.
Normal operation never goes near it. "You have to ask for it" is not the same as safe.

### The quiesce

Two halves, and both are needed:

| | |
|---|---|
| a servicer that has not started | takes the ring's busy flag, sees the quiesce, and gives the flag straight back. The check is **after** the acquire - before it, one could pass the check and take the flag after the wait had finished looking |
| a servicer already inside | is waited for, by reading the busy flags. For that wait to mean anything, `if_input()` moved back inside the flag |

Moving `if_input()` costs nothing. The buffers are re-poisoned and the doorbell is credited before the
frames go up, so the block has its credits back either way, and the only thing held out is another
servicer of the same ring - which is the one thing that must be held out.

The watchdog is drained rather than flagged, and its handler declines to re-arm while a quiesce is
set, so `callout_drain()` is final instead of racing a re-arm. `octep_dp_if_detach_all()` quiesces at
its top and resumes at its bottom, so both callers get it and `dp.if_del` - which leaves the datapath
up - can carry on afterwards.

### Testing it without paying for it

Reaching the quiesce the way the driver does takes the twelve front ports with it, one of which is the
WAN, and the last time those ports went away for a boot OPNsense dropped four interface assignments
out of its configuration. That is too much to spend on a test, so the mechanism is reachable on its
own: `dp.rx_quiesce` runs exactly the quiesce the detach path runs, and `dp.oq_busy` shows the flag and
one busy flag per served ring.

`dp.oq_busy` also carries the two numbers that answer the question a sample cannot. A servicer is
inside a ring for microseconds, so a reading taken next to one is almost always clear - which is what
the first run of this test showed, and it proves nothing either way. `waits` counts the quiesces that
had to spin at all, and `longest` the worst one in microseconds. If `waits` stays at zero under load,
the wait is decoration; it does not.

### What the test found, which was not what it was for

The first version of the quiesce was written to close a use-after-free, and the knob was added only so
the mechanism could be exercised without taking the front ports away. Hammering it found a second
defect, in the resume rather than the quiesce.

**5,285 quiesce/resume cycles over ten seconds, with a download offering 1,510 frames a second
underneath, delivered four frames.** The receive path was dead for the whole run, and the appliance was
at 100% loss to the internet immediately afterwards.

The reason is the same hardware behaviour the drain loop exists for. A quiesce turns a servicer away
*before* it clears `R_OUT_INT_STATUS`, so every interrupt arriving while the quiesce is set is taken and
discarded with the status still latched - and the block raises its interrupt on the count **crossing**
the level, not on its sitting above it. Once the quiesce lifts there is nothing left to raise one.
Clearing the status on the way out instead would lose the edge just the same.

So **resume has to look at the rings itself**, and the first version did not: it armed the watchdog 50
ticks out and returned, and the next quiesce two milliseconds later drained that timer before it could
fire. Nothing ever looked.

Resume now drains every ring before it returns, bounded like the handler's own loop, because a quiesce
taken under load leaves a backlog one pass cannot clear and no interrupt is coming to finish it.
(Sixteen sweeps of one ring's worth from every ring, now; and it arms the watchdog the way the
watchdog arms itself, because arming it for its period threw away a request for its next tick. The
same test was run again there, 2,782 cycles under a stream that did not slow: [a visit is not a pass](../findings/a-visit-is-not-a-pass.md).)

| | |
|---|---|
| 5,285 cycles, before | **4** frames delivered, 100% loss after |
| the same test, after | **21,990** frames delivered, 0.0% loss after, and a 16.7 MB fetch in 4 s |

The lesson is narrow and worth keeping: **on this block, anything that declines to service a ring owes
a service when it stops declining.** The drain loop learned it, the watchdog learned it, and the quiesce
had to learn it separately because it looked like a locking problem rather than an interrupt one.

**The watchdog had not learned it.** Its one pass over a ring the handler was working left that ring
with packets in it and nobody inside, fifty milliseconds at a time, and the handler that found the
ring held was declining with nobody owing. It showed as one TCP stream through the host that would
not go faster than 75 Mbit/s: [a visit is not a pass](../findings/a-visit-is-not-a-pass.md).

### And the number the mechanism needed

`waits 74` on that run, longest 60 us. Seventy-four times in ten seconds a quiesce found a servicer
already inside a ring and had to wait for it - which is the measurement that says the wait is
load-bearing rather than decoration, and the one a sample of the busy flags could never have given.
Without it, those seventy-four interfaces would have been freed under a servicer holding mbufs that
pointed at them.

## A bridged front port, and the filter that made one look alive while dropping every reply

A front port's hardware filter admits unicast only for the one address that port was given. That is
right for a routed port. Put the port in a bridge and it is wrong for every frame that matters: the
replies to the machines behind it carry the **bridge's** address, so none of them is admitted -
while broadcast still arrives, so ARP answers and DHCP hands out leases and the port looks perfectly
healthy. The symptom points at the firewall rules, the switch, the driver, the cable; not at the one
thing that is filtering.

The attribute that lifts it is NetAgent `0x45`, and the appliance had been getting it from a line in
the bring-up script that turned it on for ten ports unconditionally at boot. That worked and was
wrong in both directions: a routed port paid for a filter it did not need, and the setting lived in
a shell script where nothing in the system could see it or reverse it.

### The mechanism

`octep` now follows `IFF_PROMISC`. The link poll already runs on `taskqueue_thread` because the
NetAgent request sleeps; each tick it reads the flag off every front-port interface and sends the
attribute only where the answer changed. The flag is **read from the interface** rather than
recorded from `SIOCSIFFLAGS`, so there is no transition to miss and no second copy to go stale.

Two sizing decisions, both measured rather than assumed:

- The **link** read stays one port per tick - it is paid every second forever, and twelve NetAgent
  round trips a second on a control channel this project has watched go down under one unlucky
  request is not worth a faster answer to a question that moves at the speed of somebody plugging in
  a cable.
- The **filters** sweep all twelve every tick. Their conditions are false unless the stack has just
  changed its mind, so in the steady state the sweep costs twelve comparisons and no mailbox traffic
  at all - and a bridge is built by adding every member at once, so round-robin would have left the
  last member deaf for twelve seconds.

A refusal is reported once and not retried: a firmware without the attribute answers with a failed
status, and asking again every second for the life of the machine is the wrong answer to a clear no.

### What it did, on a bridge of eleven of the twelve ports

The appliance's own configuration: `bridge0` with every front port in it except the one that is the
WAN. So eleven ports want the filter open, one does not, and the driver is told nothing by anybody -
it reads `IFF_PROMISC` and acts.

```

[87] oxp1: promiscuous on
[88] oxp2: promiscuous on

**One port per second, and that is the bound rather than a coincidence.** The timestamps are
consecutive ticks: one request per invocation of the link poll, which is what stops twelve ports
from becoming twenty-four sleeping mailbox transactions in a single pass of `taskqueue_thread`. The
one gap, at `[97]`, is a tick that spent itself on the link read instead.

The same message buffer still held the boot before it, which ran the unbounded version, and the
contrast is the measurement:

```
[88]  oxp0: promiscuous on
[88]  oxp5: promiscuous on
[842] oxp1: promiscuous on      nine ports, one second, one task invocation
[842] oxp2: promiscuous on
[842] oxp4: promiscuous on
[842] oxp6 .. oxp11: promiscuous on
```

Nine requests inside one tick. Healthy, each costs about 12 ms and nobody notices; on the timeout
path each costs up to four seconds, and that is a shared single-threaded taskqueue held for most of
a minute by a driver polling a mailbox. The defect was found by review before it was seen, and the
log of the boot that had it is the reason the bound is not negotiable.

The attribute was also confirmed to work in **both** directions before any of this was trusted -
`status 0x00000000` for `param=0` as well as `param=1`, on a port with no cable, with the state put
back as found. A mechanism that can only turn a filter on would leave a port permissive forever
after it left a bridge.

**Method.** `ping -f -c 30000 -s 1472` from the appliance to a PC behind the bridged port, so every
frame is full-size and every reply is addressed to the **bridge**. The coprocessor's named counters
read before and after; elapsed time from the shell.

```

| counter | delta | per second |
|---|---|---|
| `FPCNTR_RX_WIRE` | 29,790 | 2,979 |
| `FPCNTR_TX_KN` | 29,790 | 2,979 |
| `FPCNTR_FROM_WIRE_TO_KN_FORCED` | 29,790 | 2,979 |

`Idrop 0`; `dp.tx_iq_full` 0; `dp.oq_busy` reports no ring contention and no quiesce waits.

Three things this says, and one it does not.

- **Nothing is lost on either hop.** Every counter in the six-stage chain moves by the same number,
  twice - once per direction - and the host's own `dp.rx_done` and `dp.tx_posted` had read *exactly*
  equal to `FPCNTR_RX_WIRE` and `FPCNTR_RX_KN` before the run began. Host and coprocessor agree to

- **Promiscuous mode costs nothing measurable.** 0.328 ms average with the filter open, against
  0.459 ms on a lighter run and 0.63 ms on the first three frames; the spread is scheduling, not the

- **`FROM_WIRE_TO_KN_FORCED` equals `RX_WIRE` exactly**, every frame, which is the same reading that
  settled [#221](https://github.com/AbdelmonemAwad/os-xgs-npu/issues/221): with no flow installed,
  the fast path forwards everything to the host and accelerates nothing. A bridge does not change
  that.

**It does not establish a ceiling.** 2,979 frames a second is lower than the 5,003 further up this
page, and the difference is the far end: this run answers a Windows PC rather than a router, 0% was
lost, and not one of the driver's pressure counters moved. Nothing here was stressed, so this is a
floor on what the path can do and not a limit.

### `FPCNTR_TX_DROP` is 146, and it is from start-up

The first reading after the boot showed `FPCNTR_TX_DROP` and `FPCNTR_TX_DROP_QUEUE_FULL` both at
146, which reads like a 4.6% loss toward the host. It is not: across a 3,000-frame run and then a
30,000-frame flood, **neither counter moved at all**. The 146 was spent once, during bring-up, while
the rings were being armed and before the logical interfaces existed - which is where a frame has
nowhere to be delivered by construction.

Worth recording because the snapshot alone would have been read as an ongoing loss, and the only
thing that distinguishes the two is a second reading under load. A counter with no derivative is
a fact about the past.

## ~~Jumbo frames are not available, and the number is 1506~~

~~Jumbo frames are not available, and the number is 1506.~~ Struck 2026-10-12: a port's MTU is
any value from 72 to 9,000 since that day, the coprocessor having always written a long frame over
as many buffers as it needs - see [the MTU is the LIF's](../findings/the-mtu-is-the-lifs.md) and
[the rows below](#the-mtu-from-72-to-9000-on-the-spot). The arithmetic that follows was right
about one buffer and wrong about the limit; it stays as it was written.

Asked for directly, and the answer is in the ring rather than in the hardware. The receive ring is
programmed with one buffer size, which the live register dump confirms as `BSIZE 1602`:

    OCTEP_DP_BUF_SIZE     = 1536 + 66 (the private tag)   = 1602
    OCTEP_RX_PREFIX_LEN   = 82         (the far side writes its own prefix into the same buffer)
    Ethernet header       = 14
    OCTEP_DP_IF_MTU_MAX   = 1602 - 82 - 14                = 1506

So `ifconfig oxpN mtu 1506` is accepted and 1507 is not, and `mtu 9000` cannot be honoured by asking
for it: the far side would write a 9,000-byte frame plus an 82-byte prefix into a 1,602-byte buffer.
Jumbo frames on these ports are a ring-sizing change - a larger `BSIZE` published to the coprocessor
at ring-arm time, which is latched once per coprocessor boot - and not a configuration setting.

Recorded because the clamp has been wrong once already in the other direction: it read
`OCTEP_DP_BUF_SIZE - 128` = 1474, below the 1500 every one of these interfaces actually runs at, so
`mtu 1500` failed with `EINVAL` and a port lowered to 1474 could not be raised again without a
reboot.

## The first connection through the tunnel, and where the MSS clamp has to sit

2026-10-12, module `c12b6dfd`, for [issue 321](https://github.com/AbdelmonemAwad/os-xgs-npu/issues/321):
the first TCP connection a LAN machine opens through the tunnel stands still for 0.3 s while it
learns the path's MTU - ten 1,460-byte segments with DF, ten "fragmentation needed" answers from
the appliance, a 300 ms retransmission timer. The issue said what would remove it, a maximum MSS
on the tunnel's traffic, and did not try it. Tried, in three forms, on the lab tunnel over the 10G
path, one connection from the LAN machine each time with the far end capturing the decrypted side
and the appliance's `ipsec.out_needfrag` read before and after:

| setting on the appliance | the SYN's MSS as the far end received it | `ipsec.out_needfrag` | the connection |
|---|---|---|---|
| none | - | +11 | the machine learned a path MTU of 1,446 |
| a normalisation rule, `scrub in on <the member port> proto tcp to <the far end> max-mss 1406` | 1460 | +0 | 1 MB in 10 ms - the machine's own memory of the path, not the rule: the rule matched no packet at all (evaluated 102,713 times, 0 packets), because OPNsense's `scrub in all` comes after it and the last matching normalisation rule wins |
| the interface's MSS field on the member port the machine is cabled to: `scrub on oxp5 inet all max-mss 1406` | 1460 | +0 | the same; the rule matched 38 packets and clamped nothing: the machine's packets reach pf on the bridge, not on the member |
| **the interface's MSS field on the bridge, the LAN: `scrub on bridge0 inet all max-mss 1406`** | **1406** | **+0** | 1 MB in 10 to 30 ms, no pause over 100 ms, no segment over 1,406 |

So the remedy is the MSS field of the interface pf sees the LAN machine on - the bridge here - set
to the tunnel's MTU plus forty, 1,446. Nothing in the driver.

Three things the measuring found about itself. The Windows machine's memory of a path's MTU
outlives what `netsh interface ipv4 show destinationcache` lists, and the peer's keep-alive pings
to it refreshed that memory, so two "after" runs read 1,406-byte segments from a machine that had
not been clamped; the SYN's MSS at the far end is the reading that cannot be fooled that way, and
is the column above. The first run's client sent no mode byte to the far end's server and was
reset before it could time anything, so the 0.3 s itself is the issue's own reading of 2026-10-08
and not this day's. And `out_needfrag` rose by ten between two runs while nothing of the tool's
was running and the pinger was stopped: a first connection from the machine that was not this
tool's; which, not known.

So RESEND changes nothing, which says the count was not sitting at the level when a burst began -
the ring was empty, the burst crossed the level, and still no handler ran within a watchdog
period. And the one stall the third build caught says why, in the block's own registers as they
stood before the watchdog touched the ring:

```
before it: int_status 0x1  cnts 0x4000143c00000038  levels 0x5600000001
```

`int_status` 0x1: the block's latched interrupt status was **set**. `cnts`: 0x38 = 56 packets in
the low word, the register's own "output interrupt" flag (bit 62) set in the high one. `levels`: a
packet threshold of 1. The condition was there, latched, for 128 ticks with 56 packets behind it,
and the handler did not run. This is not the block failing to raise the interrupt; it is the
interrupt raised and not acted on - the MSI-X message not delivered, or delivered to a vector that
did not run the handler. The next instrument is on that side: the vector's MSI-X mask bit and its
PBA pending bit and the vector's count from the kernel, read at the same moment, and a second read
of the status right after a visit's clear, for a clear that lost a race with the block setting it.
Every pass of all three hours was clean, so the net under this is still a net.

## How to take these again

Everything here is taken with four things in [tools/](../../tools), which are meant to be copied to
the appliance and run there:

| | |
|---|---|
| `blast.c` | a UDP sender that does not wait, and paces itself when given a rate |
| `octep-fpcnt.sh` | the coprocessor's 182 counters, **with their names** |
| `octep-fairness.sh` | the sweep above: what load on one port costs the others |
| `octep-soak.sh` | hours of traffic, with a leak, a stall and a starvation test in the log |

`fpcntr-names.txt` is the list those names come from - the enum in the shipped module's DWARF, in
the array's own order. Nine of its indices were already known from live traffic before the list
existed and every one of them lands on the right name, which is the reason to trust the other 173.
Without it a counter read is a column of integers: index 18 means nothing until it reads
`FPCNTR_TX_WIRE_ERR`.

The generator binds a source address, sends to a destination port nothing listens on, and never
waits:

```
blast <bind-ip> <dst-ip> <payload-bytes> <seconds> [packets-per-second]
```

Point it at a port with **no cable**, with an address on that interface and a static ARP entry for a
neighbour that does not exist, so nothing is ever asked for and nothing leaves the appliance:

```
ifconfig oxpN inet 198.51.100.1/24 alias
arp -s 198.51.100.2 02:00:00:00:00:02
...
arp -d 198.51.100.2 ; ifconfig oxpN inet 198.51.100.1 -alias
```

Read the counters with `netstat -i -b -n`, and **mind the columns**: `Ipkts` is `$5`, `Ibytes` is
`$8`, `Opkts` is `$9`, `Obytes` is `$11`. `$7` is `Idrop`, and reading it as `Opkts` once produced a
confident wrong conclusion that the transmit counters were dead.

The far side's named counters come over `rpc` command 44 with `rpc.num_entries` set - see
[octeon-tx.md](../families/octeon-tx.md) for the reader and for the 182 names in order.
