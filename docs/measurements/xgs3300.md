# XGS 3300 - what has been measured on it

Numbers taken on one appliance, with how each was taken and what it does not mean. They are here
rather than in [octeon-tx-reference.md](../families/octeon-tx-reference.md) because a measurement
belongs to a **board**, not to a family: a second XGS 3300 with a different kernel or a different
cable would produce different figures, and the reference page should carry conclusions rather than
readings.

**Nothing here is a projection.** Every line was read off this machine.

## The machine

| | |
|---|---|
| appliance | Sophos XGS 3300, assembly `AMDA0202-0004`, platform `xgs1us` |
| host | AMD Ryzen Embedded V1780B |
| coprocessor | Cavium OCTEON TX CN8365, PCI `177d:a300` at `pci0:1:0:0` |
| operating system | OPNsense 26.7 / `FreeBSD 15.1-RELEASE-p1 stable/26.7-n283674-12334a596709 SMP` |
| driver | `octep`, built on the appliance against that kernel's own headers |
| front ports | 12, all presented as `oxp0`..`oxp11` |

## Round trip and loss

**Method.** `ping -f` from the appliance to the router on the other end of a copper panel port's
cable, 30,000 full-size frames, interface counters read either side.

```
elapsed 6 s
in   30022 pkts   1512 bytes/pkt    5003 pps    60 Mbit/s
out  30003 pkts   1513 bytes/pkt    5000 pps    60 Mbit/s
0.0% packet loss
round-trip  min 0.091   avg 0.193   max 0.508 ms
```

**What it is.** A latency figure and a loss figure. Nothing dropped in 30,000 full-size frames.

**What it is not.** A throughput figure. `ping -f` sends the next probe when the last reply arrives,
so it is bound by the round trip: 5,000 packets a second against a 0.193 ms round trip is the same
number written twice.

## The transmit ceiling

**Method.** A UDP sender that never waits (`blast.c`, below), aimed at **a panel port with no cable
in it** so the frames cross the whole host-to-coprocessor path and die at a dark switch port without
touching anything anyone else is using. Five seconds, 1472-byte payloads. The coprocessor's own
named counters were read either side of the run over the `rpc` facility.

```
offered and accepted by the driver     2,628,609     525,722 pps
FPCNTR_RX_KN                          +2,627,710     the coprocessor took them
FPCNTR_FROM_KN_TO_WIRE                +2,628,609     and chose the wire for every one
FPCNTR_TX_DROP_QUEUE_FULL             +2,210,885     84% refused at its egress queue
to the wire                              416,825      83,365 pps = 1,023 Mbit/s
```

**The account closes.** 1,023 Mbit/s is line rate for a gigabit port at 1534 bytes a slot with the
preamble and the interframe gap, so everything the driver posted either left at line rate or was
dropped by the coprocessor's egress queue - which is the correct thing for it to do.

**So the number that matters is what the driver accepts:**

| | packets a second | |
|---|---|---|
| the driver accepts | **525,722** | measured |
| a 1G port needs | 81,486 | **6.5x headroom** |
| a 10G port needs | 814,863 | **65% of line rate** |

For the eight copper panel ports and the two 1G cages this driver is nowhere near the bottleneck.
Only the two 10G SFP+ cages are capped.

## Removing a redundant write

**Method.** The same generator and the same dark port, before and after the change in #173, which
stopped the transmit path zeroing the frame it was about to copy over.

| payload | before | after | |
|---|---|---|---|
| 1472 bytes | 525,722 pps | **535,142 pps** | +1.8% |
| 64 bytes | 595,558 pps | **607,232 pps** | +2.0% |

**What it tells us beyond the gain.** 525,722 packets a second is 1.9 microseconds each, and a
redundant 1,514-byte write is not what that is made of. The next suspect is the one MMIO write per
packet - the input doorbell.

## Two counters that were wrong, and how the measuring found them

**Received bytes were doubled.** The first run charged an interface **3,026 bytes for every
1,514-byte frame**. `ether_input_internal()` adds the received byte count itself unless the driver
claims `IFCAP_HWSTATS`, which this one does not, so counting it in the driver as well doubled it.
The packet count was right, because that file increments no `IPACKETS`. Fixed in #171; afterwards
the two directions agree at 1512 and 1513 bytes a packet, which is what a ping flood should show.

**`Opkts` is offered load, not what left the port.** In the ceiling run it read **6,432 Mbit/s out
of a gigabit port**: the 84% the coprocessor dropped, counted as sent. The driver cannot see those
drops per packet - they belong to the far side and only `rpc` reads them - so read `Opkts` as
offered load and `FPCNTR_TX_DROP_QUEUE_FULL` as the truth about what the wire took.

## How to take these again

The generator is on the appliance as `/root/npu/blast.c`; it binds a source address, sends to a
destination port nothing listens on, and never waits:

```
blast <bind-ip> <dst-ip> <payload-bytes> <seconds>
```

Point it at a port with **no cable**, with an address on that interface and a static ARP entry for a
neighbour that does not exist, so nothing is ever asked for and nothing leaves the appliance:

```
ifconfig oxpN inet 198.51.100.1/24 alias
arp -s 198.51.100.2 02:00:00:00:00:02
...
arp -d 198.51.100.2 ; ifconfig oxpN inet 198.51.100.1 -alias
```

Read the counters with `netstat -i -b -n`, and **mind the columns**: `Ipkts` is `$5`, `Ibytes` is
`$8`, `Opkts` is `$9`, `Obytes` is `$11`. `$7` is `Idrop`, and reading it as `Opkts` once produced a
confident wrong conclusion that the transmit counters were dead.

The far side's named counters come over `rpc` command 44 with `rpc.num_entries` set - see
[octeon-tx.md](../families/octeon-tx.md) for the reader and for the 182 names in order.
